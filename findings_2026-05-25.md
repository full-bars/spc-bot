# Detailed findings by subsystem

## 1. `cogs/` (Discord handlers, task loops)

### Critical / High

**[H] `/md` command is broken — tuple treated as list** — ✅ VERIFIED
`cogs/status.py:925` `md_numbers = await fetch_latest_md_numbers(fresh=True)`.
`fetch_latest_md_numbers` is typed `-> Tuple[Optional[List[str]], bool]` (`cogs/mesoscale.py:40`)
and every `return` returns a 2-tuple. `status.py` never unpacks it: `len(md_numbers)` logs `2`,
`if not md_numbers` is always falsy, and iterating yields the list *and* the bool — so the bool
gets passed downstream. The `/md` command will misbehave whenever MDs are active. **Real, fix:**
`md_numbers, _ = await fetch_latest_md_numbers(fresh=True)`.

**[H] "View Environment" button can crash with TypeError** — ✅ VERIFIED
`cogs/warning_ui.py:35-48`. The guard `if not row or not row["gif_path"]:` only `return`s when a
`RecorderCog` exists. If `row` is `None` (or `gif_path` is `None`) **and** there's no recorder cog,
it falls through to `gif_path = row["gif_path"]` → `TypeError: 'NoneType' object is not
subscriptable`, the interaction hangs with no user feedback. Add an unconditional `return` /
`followup.send` in the not-found branch.

**[H] Mark-posted-before-send drops posts on failure** — ✅ VERIFIED (two sites)
- `cogs/reports.py:198` calls `await add_posted_report(product_id)` *before* `channel.send(embed=embed)`
  at ~`:217`. If the send raises (403/429/network), the LSR is permanently marked posted and never retried.
- `cogs/mesoscale.py:608` `self.bot.state.posted_mds.add(md_num)` runs before the fetch+`channel.send`;
  a send failure silently loses the MD.
Compare the NWS-warning path which uses a `claim_posted_warning` context manager *with rollback* —
that's the pattern these two should follow.

**[H] `nwws.py` ping loop sets reconnect flags on every exit** — ✅ VERIFIED
`cogs/nwws.py:185-186`. `self.reconnect = True` / `self.use_ipv6 = False` are dedented to the
`try` level, so they run on **normal exit, CancelledError, and any exception** — not just the
intended cancellation case. After an intentional `cog_unload` / standby demotion this keeps slixmpp
reconnecting. Indent them into the `except asyncio.CancelledError:` body (or wherever reconnect is
actually intended).

**[H] `asyncio.create_task` inside a synchronous slixmpp callback** — ✅ VERIFIED
`cogs/nwws.py:296`. `NWWSClient.message()` is a sync slixmpp handler; `asyncio.create_task` relies on
the *currently running* loop being discord.py's. The ping loop already uses `self.bot.loop.create_task`
(line ~169) — use the same here to guarantee the task lands on the right loop.

**[H] `radar/downloads.py` module-global progress state races across users** — (lead)
`cogs/radar/downloads.py:29-30` `progress_data = {}` / `progress_lock` are module-level. Concurrent
`/download` invocations share one dict; one call's `progress_data.clear()` in `finally` wipes the
other's. Key by invocation UUID or pass per-call state.

**[H] PIL Image handles leaked in GIF worker** — ✅ VERIFIED
`cogs/recorder.py:286` `frames = [Image.open(f) for f in frame_paths]` are never closed (~18 handles
per recording mission). Use context managers / explicit `close()` in a `finally`.

**[H] Sounding dedup claim is memory-atomic, not Redis-atomic** — (lead)
`cogs/sounding.py:690-701`. The in-memory `posted_soundings.add(pkey)` happens before the awaited
`add_posted_sounding` Redis write. A concurrent monitor tick can read Redis in that gap, miss the key,
and post a duplicate. The "claim atomically" comment overstates the guarantee.

### Medium (selected)

- **`mesoscale.py:33` `asyncio.Lock()` created at import time** — may bind to the wrong/absent event
  loop on 3.10+; create lazily in `cog_load`. (lead)
- **`status.py` live status view fetches `ipinfo.io/ip` every 5s** (`build_embeds`) — 12 needless
  external calls/min; cache it. (lead)
- **`warnings.py:580-594` cancellation image retry** does up to ~8s of sequential `asyncio.sleep`
  inside the post coroutine — during an outbreak many of these queue up. Consider firing as a
  background task. (lead)
- **`mesoscale.py:738` lambda done-callback** calls `t.exception()` without guarding the
  already-cancelled case; the file already defines `_log_task_exception` — use it. (lead)
- **`watches.py:229` file opened in a `to_thread` lambda, never closed** — `open(p,"rb").read()`
  leaks the fd until GC. Use `with`. (lead)
- **`reports.py:444-448`** can `set_image()` to a just-404'd IEM URL and send `file=None`, producing
  a broken embed image. (lead)
- **`sounding.py:811` `auto_sounding_watches`** checks `is_primary` *before* `wait_until_ready()`;
  during async failover promotion it can early-return and miss the 00z/12z window. Gate ready first
  (or in `before_loop`). (lead)

### Low / smells
- `warning_format.py:35` state-list typo `"NORTH DACOTA"` (regex has the correct spelling) — the
  garbage-filter never matches real "NORTH DAKOTA" fragments. (lead)
- `warning_format.py` `_DESCRIPTION_LIMIT = 4000` defined but unused; concise warning text has no
  hard length cap → risk of >4096-char embed rejection. (lead)
- `reports.py:37` `PNSView(timeout=86400)` has no `custom_id` and isn't registered via
  `bot.add_view()` — the button silently dies after any restart/deploy. (lead)
- `mesoscale.py` hardcodes `[:4090]` in 3 places instead of the defined `EMBED_BODY_LIMIT`.
- Duplication: `post_md_now` ≈ `auto_post_md`; watch-embed building repeated 3×. Long functions:
  `_tick()` (warnings, 126 LoC), `post_soundings_for_watch` (165), `download_and_zip` (380).

## 2. `utils/` & `models/`

### Critical / High

**[H] `render_tornado_track()` runs synchronously on the event loop** — ⚠️ line ref was wrong, substance confirmed
The utils agent cited `map_utils.py:198`, but that file is only 108 lines — the line number was
fabricated. **The real issue is confirmed:** `render_tornado_track` (`utils/map_utils.py:19`) is a
sync function doing cartopy OSM tile downloads + 120-DPI matplotlib render, and it is called
**directly** (no `run_in_executor`) at `cogs/warning_ui.py:198` and `cogs/reports.py:421`. During a
tornado outbreak each call stalls the entire event loop (heartbeat, dedup, Redis) for seconds. Wrap
both call sites in `await loop.run_in_executor(...)`.

**[Med→High] `http_get_json` doesn't retry HTTP 500** — ✅ VERIFIED
`utils/http.py:368`. 429/502/503/504 raise a retriable `ClientResponseError`, but any other non-200
(incl. 500) hits `circuit_breaker.record_failure(host); return None` — a *normal return* inside the
tenacity-wrapped function, so no retry happens. `http_get_bytes_conditional` (uses `raise_for_status`)
does retry 500s, so the behavior is inconsistent across the two fetch helpers. Decide whether 500 is
retriable and make both paths agree.

**[Med] `get_events_db()` singleton has no init lock** — ✅ VERIFIED
`utils/events_db.py:43`. Two concurrent first-callers both see `_db is None`, both
`await aiosqlite.connect()`, and one connection is orphaned (a WAL write connection leak).
`utils/db.py` does this correctly with `_LOCK` + double-checked locking — mirror that here.
(Agent rated Critical; downgraded to **Medium** — only reachable in a narrow startup race.) 🔻

### High / Medium (selected, leads)
- **`map_utils.py:105-107` figure leak on `savefig` raise** — `plt.close(fig)` only on the happy path;
  wrap in `try/finally`. (Note: there *is* a `plt.close(fig)` at line 49 for the early-return path,
  so this is narrower than stated.)
- **`state_store.py` invalidate-before-write** — write fns call `_cache_invalidate` then `await`
  the SQLite write; a concurrent reader in that window sees the stale pre-write set. Prefer
  `_cache_set` *after* the write succeeds. (lead)
- **`events_db.py:198 backfill_dat_guids`** accumulates UPDATEs and commits once at the end; any
  exception in the loop → `except` swallows it, commit never runs, all work lost and re-attempted
  every cycle. Commit in batches or in a `finally`. (lead)
- **`discord_gateway.py:55` `asyncio.get_event_loop()`** — deprecated; use `get_running_loop()`. (lead)
- **`http.py:182 _get_retry_after()` is dead code** — `Retry-After` header is parsed but never used;
  429s back off at most ~10s regardless of server-mandated delay. (lead)
- **`state_store.py:232 _cache` has no size cap** — TTL-only eviction; bounded in practice but can
  balloon during a burst day. (lead)
- **`http.py` retry-count semantics differ** — `http_get_json(retries=N)` = N+1 attempts vs
  `http_get_bytes_conditional(retries=N)` = N attempts; `fetch_with_validators` compounds to
  ~2×(retries+1) requests. (lead)
- **`state_store.py:1081 mirror_to_sqlite()` skips `posted_surveys` and `posted_soundings`** —
  after failover promotion the new primary may re-post surveys/soundings. **Worth checking** given
  the failover architecture. (lead)
- **`dat_api.py:27` GUID interpolated into ArcGIS WHERE clause** without `urllib.parse.quote` — not
  SQLi (REST API), but a quote in the GUID silently breaks the query → no map. (lead)
- **`db.py:63 _write_failure_count`** resets on any single success, so a flapping DB never reaches
  the 5-consecutive-failure alert threshold. (lead)
- **`geo.py:83` Python fallback for `points_in_polygon_counts` returns all zeros** — silent wrong
  results if Rust is ever unavailable; should at least warn. (lead)

## 3. `src_rust/lib.rs` + `lib/` (Rust core & VAD/VTEC)

> PyO3 0.21+ wraps Rust panics in `catch_unwind` → Python `RuntimeError`, and most call sites have a
> Python fallback. So "panics" here generally mean a failed *call* (caught), not a process crash.

### Critical (with caveats)
- **`scan_to_ci` byte-slice can panic on multi-byte UTF-8** (`lib.rs:817`) — `slice[..nlen]` where
  `nlen` is an ASCII needle's byte length can split a UTF-8 char boundary. Affects
  `parse_warning_polygon`, `parse_md_number`, `parse_watch_number`, `extract_narrative`. NWS products
  are ASCII in practice and the Python fallback catches the RuntimeError, so **real-world impact is
  low** — but a defensive `is_char_boundary` check (or use the already-available `Lazy<Regex>`) would
  remove it. Also see L4: this fn heap-allocates a `String` per byte position (O(N·M)). (lead)
- **`vad_reader.py:315` `page[0]` IndexError on empty tabular page** — the Rust tabular parser returns
  `None` first and triggers exactly this Python fallback, so it's reachable on malformed VWP data. (lead)
- **`vad.py:56` `parse_time` double-prefix on month rollover** — a bare `DD/HHMM` that looks like a
  future time gets year-month prepended to an already-prefixed string → `ValueError`. (lead)

### High / Medium (leads)
- **`lib.rs:1679` unbounded MPSC channel** for NWWS messages — no backpressure; a slow Python
  consumer during a high-volume event can grow memory without bound. `nwws_stats` exposes
  received−drained for monitoring but there's no automatic mitigation. **Worth a bounded channel
  or a drop policy.**
- **`lib.rs:1661` `reconnect_count` not incremented on mid-session disconnects** (only on `join_muc`
  failure); `messages_filtered` actually counts *forwarded* messages — misleading metric names.
- **`lib.rs:615` `compute_critical_angle` clips at `6000.0` but altitudes are km** → the 6 km clip is
  a no-op. **Latent only** — this exported fn isn't called from Python (`params.py` uses
  `compute_crit_angl`), so current impact is zero.
- **`wsr88d.py:227-231` `KeyError` on unknown radar IDs** — `_radar_info[radar_id]` with no guard
  propagates to the Discord command. (Hodograph validates against an allowlist first, which mitigates
  the `/hodograph` path.)
- **`asos.py:22` isotropic degree approximation** `deg = radius_km/111.0` for lon too → at 60°N the
  E-W box is ~half the intended radius (misses Alaskan ASOS stations). Use `cos(lat)` scaling.
- **`lib.rs:1648` `eprintln!` for all XMPP logging** including a 30s heartbeat timeout — floods
  journald and bypasses Python logging config.
- **`wsr88d.py:141` typo `'KTYX': {'wfo': 'BKTV'}`** should be `'KBTV'` (Burlington VT) → wrong TGFTP
  HAS filenames (404); S3 fallback masks it.

**Parser cross-check (good news):** Rust and Python VTEC/polygon/altitude parsers are **consistent**;
Rust is authoritative, Python is a verified fallback. The dead 3-char WFO normalization branch exists
(harmlessly) in both.

## Cross-cutting themes

1. **"Mark-posted-before-send" is a recurring anti-pattern.** reports.py and mesoscale.py both commit
   dedup state before the Discord send and don't roll back on failure → silent permanent drops. The
   warnings cog already solved this with a `claim_*` context manager + rollback. **Standardize on that
   pattern across all post paths.** (Highest-leverage reliability fix.)

2. **Sync CPU/network work on the asyncio event loop.** `render_tornado_track` is the clearest
   offender (matplotlib + cartopy tile fetch, called directly). Audit all matplotlib/cartopy/PIL and
   blocking file reads for `run_in_executor`. (The cogs agent notes most heavy paths *do* offload —
   the tornado-track render is the gap.)

3. **Dedup "claims" that are memory-atomic but not store-atomic** (soundings; the cache
   invalidate-before-write window). Under concurrency these can double-post. Where Redis is the source
   of truth, claim in Redis first (e.g. `SET NX`) before the in-memory add.

4. **Test coverage is concentrated on failover/dedup/DB and absent on the radar + NWWS + sounding
   render paths** — i.e. the live-data ingestion paths that matter most for missed/duplicate alerts.

5. **Subagent line numbers are not 100% reliable.** I caught one fabricated ref (`map_utils.py:198`).
   Verify before acting on any (lead)-tagged finding.
